BEHIND THE SCENES
You type youtube.com and press Enter
From keypress to rendered page — 12 layers of infrastructure firing in under 300ms.
12 steps ~8 min read #1 interview question
1
PHASE 1 — BEFORE THE NETWORK
Browser Cache & OS Hosts File
Before any network packet leaves your machine, the browser checks 4 caches in order: browser DNS cache (chrome://net-internals/#dns) → OS DNS cache → /etc/hosts file → OS resolver. On a repeated visit, DNS resolves in 0ms — pure cache hit.
💡
Senior insight: Adding 127.0.0.1 api.myapp.local to /etc/hosts is how local HTTPS dev works without running a real DNS server.
2
PHASE 2 — DNS RESOLUTION
The Recursive Resolver Walk
Your ISP's recursive resolver asks the root nameservers (there are only 13 root server clusters on Earth), which delegate to .com TLD servers, which delegate to YouTube's authoritative nameservers, which return 142.250.x.x with a TTL. The whole walk takes ~50ms if nothing is cached.
$ dig +trace youtube.com
; → root → .com TLD → youtube.com NS → 142.250.80.46
3
PHASE 3 — TCP + TLS
3-Way Handshake → TLS 1.3 in 1-RTT
SYN → SYN-ACK → ACK establishes a reliable channel. Then TLS 1.3 negotiates encryption in a single round-trip (vs. 2 in TLS 1.2). The certificate chain is verified against your OS trust store. HSTS means the browser refuses HTTP even if you type it.
DEPLOYMENT VARIANTS — where the request lands
🖥 EC2 / Bare Metal
Nginx listens on :443 → reverse proxies to Node/Gunicorn on :3000 → your route handler
☸ EKS / Kubernetes
ALB → Ingress controller → Service (ClusterIP) → Pod → container port
⚡ Serverless
API Gateway → Lambda cold start (or warm) → your function handler → response
🎯 INTERVIEW ANSWER SCAFFOLD
When asked "walk me through what happens when you type a URL" — start with browser cache, then DNS hierarchy, then TCP+TLS, then HTTP/2 multiplexing, then CDN edge, then load balancer, then reverse proxy. Mention stateful vs stateless. Name the deployment target. Most candidates stop at DNS. You won't.
